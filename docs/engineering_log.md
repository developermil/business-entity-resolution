# Business Entity Resolution — Amazon ML Challenge (72h Hackathon)

Status snapshot for anyone (human or LLM) picking this project up mid-flight.

## 1. Challenge background & goal

**Platform**: Unstop, live public/private leaderboard, 72-hour window, unlimited submissions (no negative marking).

**Task**: Business Entity Resolution. Three independent, noisy data sources describe businesses:
- **Source 1** — the deduplicated reference set. Every Source-1 entity needs zero, one, or more matches from Source 2 and/or Source 3.
- **Source 2 / Source 3** — records to match against Source 1.

Each record has `entity_id`, `business_name`, `business_address`, `country`. Training data covers `US`/`India`; the **test set also contains `France`**, unseen in training — country must be treated as an auxiliary feature, never a hard filter or one-hot category, or French entities silently fail to match.

**Noise patterns to expect** (explicitly called out in the brief): name abbreviations, legal-suffix inconsistencies (Pvt/Private, Ltd/Limited, Corp/Corporation), punctuation, **word-order transpositions**; address abbreviations, transliteration variants, missing components, landmark references, **component reordering**.

**Files**: everything is `.tsv` (tab-separated) — read with `sep="\t"`, not default CSV parsing.

**Outputs required**:
- `matching_results.tsv` (`source1_entity_id`, `matched_entity_ids`) — **the only file scored** on the leaderboard.
- `candidate_pairs.tsv` (`source1_entity_id`, `candidate_entity_ids`) — the blocking/candidate-generation output fed into the matcher. Not scored, but validated: every ID in `matching_results.tsv` must appear in the matching row of `candidate_pairs.tsv`.

**Hard format rules**: every Source-1 test entity must appear exactly once in both files; empty string (not omission) for singletons; no duplicate IDs; IDs must be real Source-2/3 test IDs.

**Metric**: **F_0.5 score, macro-averaged per Source-1 entity.** Precision weighted 2× over recall — a false merge (wrong match) costs more than a missed match. Singletons score 1.0 for a correctly-predicted empty list, 0.0 for any wrong guess — so how common singletons are (see Progress below) directly affects how conservative the matching threshold should be.

**Constraints**: no external data lookups/APIs/geocoding of any kind (instant disqualification if caught); any model used must be MIT/Apache-2.0 licensed and ≤8B parameters; final submission is a zip with `output/` (both TSVs), `code/business_entity_resolution/` (runnable pipeline + README + requirements.txt), and a filled-in methodology doc.

## 2. Phased plan

- **Day 1 (0–24h)** — environment setup, EDA, a working (even if rough) blocking + matching pipeline, **first leaderboard submission**. Skip: deep learning embeddings, hyperparameter tuning, elaborate feature sets, polished docs.
- **Day 2 (24–48h)** — improve blocking recall, swap the rule-based/simple classifier for a properly tuned one, retune the F_0.5 threshold, handle noise patterns and the unseen-country case more robustly, submit multiple times to track improvement.
- **Day 3 (48–72h)** — precision push (F_0.5 rewards this most), final packaging: methodology doc, code zip, `validate_submission.py` clean run, submit with buffer before deadline.

## 3. Progress so far

- Read the problem statement PDF directly (it's an image-based/scanned PDF, extracted via page rasterization, not text extraction).
- Explored dataset scale: **~2.34 GB total**, **~5M rows per source file** (~15-30M records across S1/S2/S3, train+test). **Singleton rate in train ground truth: 5.6%** — most Source-1 entities *do* have a real match, so blocking recall matters more than usual; don't over-tune toward conservative thresholds.
- **Deeper EDA (from a parallel Claude Code session working directly against the dataset) surfaced two structural findings that reshaped the blocking strategy**:
  - **Zero cross-country matches** across 7.64M ground-truth pairs — US only matches US, India only matches India. This makes country a *perfect, free* blocking partition (no recall cost), not just a soft feature.
  - **Country distribution shifts hard between train and test**: train is US 60%/India 40%; test is India 46.7%/US 38.3%/**France 15.0% (259,452 S1 records)** — France is completely unseen in training, so nothing in the pipeline may hard-code to specific country values.
  - **1-to-1 target constraint**: every Source-2/3 record matches *at most one* Source-1 entity (verified: 0 multi-links in ground truth), and ~25-27% of Source-2/3 records are pure non-matching distractors.
- Compute environment went through several iterations (see Bottlenecks) — currently running on **Google Colab free tier** (~12.7 GB RAM, no GPU needed), reading data directly from an **S3 bucket** via `pandas` + `s3fs`, with AWS credentials in Colab's Secrets manager.
- **Root cause of the OOM crash properly diagnosed** (via a parallel debugging session that measured actual peak RSS memory): it wasn't total data volume — it was **windowed sorted-neighborhood blocking's worst case**. A handful of key values (blank addresses, very common name tokens) get shared by tens/hundreds of thousands of records at real scale; sliding a window across a tie-block that size still emits `window` pairs *per record in it*, across 3 key types × 3 random passes, with every pass held in memory before final dedup. That's what exhausted RAM, not the base data (which is only a few GB even at 15-30M rows).
- **Current architecture (v8)** replaces windowed blocking entirely with a **capped hash index**: for each of 3 normalized keys (sorted name tokens, name prefix, sorted address tokens), any key value shared by more than `MAX_POOL_BLOCK_SIZE` pool records is dropped for that key type — near-zero discriminative value anyway, and this is what makes memory bounded regardless of data skew. The index is now also **partitioned by country first** (the EDA finding above), and candidate generation streams Source-1 in `CHUNK_SIZE`-row batches straight to a TSV on disk — nothing about a finished batch stays in memory, so peak memory depends on the chunk size, not total row count.
- **Matching**: `rapidfuzz` token-sort-ratio on name + address, plus a generic (not hard-coded) `country_match` feature → `LogisticRegression` (`class_weight="balanced"`) → threshold tuned by directly maximizing macro F_0.5 on a held-out validation split.
- **1-to-1 post-processing**: since a Source-2/3 record can only really belong to one Source-1 entity, if two Source-1 entities both clear the threshold for the same candidate, only the higher-confidence claim is kept — verified in testing to produce a final output where every matched ID is provably unique.
- **`print_mem()` checkpoints** (stdlib `resource` module) after every heavy step, and a local **self-check cell** replicating the organizers' structural rules (plus the 1-to-1 property) so a formatting mistake surfaces before spending a real submission on it.
- **Current file**: `entity_resolution_starter.ipynb` (v8) — validated end-to-end on synthetic data specifically designed to stress-test the new logic (mixed countries, an oversized blank-address distractor block, forced tiny chunk sizes): confirmed **zero cross-country candidate leakage**, correct block-size capping, and correct 1-to-1 de-duplication.
- **First real run against actual S3 data started, hit a new memory issue in Section 4 ("Normalize text + build blocking keys")**: baseline RAM right after loading (Section 3, post `del train_s2, train_s3` + `gc.collect()`) was **4.4 GB**, but running `build_keys()` on `train_pool_all` (~10.2M rows) pushed RAM past **9 GB** — roughly **4.6 GB added by a step that should only add three small string-key columns**. Root cause: `build_keys()` did `df = df.copy()` on entry (duplicating the entire ~10.2M-row pool frame for no reason, since the result is reassigned onto the same variable — no aliasing to protect against) and held both `name_norm_tmp` and `addr_norm_tmp` (each a full 10M-row object-dtype Series) in memory simultaneously.
- **Fix applied (round 1)**: removed the `.copy()`, mutate the frame in place, process name-keys then address-keys sequentially with `del`+`gc.collect()` between them, added `print_mem()` checkpoints inside `build_keys()`. Session restarted and re-run clean. **Result after round 1, measured via peak-RSS checkpoints**: `build_keys(train_s1)` → 6,132 MB, `build_keys(train_pool_all)` → 9,253 MB, `build_id_codec` (dict-based `entity_id → code` map + `.map()`) → **10,347 MB**. Still hitting the same ~10.3 GB ceiling after a genuinely clean restart — meaning the problem isn't leftover state from a prior run, it's the **actual working-set size of the current design** at real (~10.2M-row) scale.
- **Diagnosis (round 2)**: the remaining cost is baseline object-dtype overhead, not a fixable "bug" — pandas stores every string as a separate boxed Python object (~50-100+ bytes of overhead *per string*, on top of the characters themselves). At ~10.2M pool rows × 4 raw text columns (`entity_id`, `business_name`, `business_address`, `country`) + 3 derived key columns, that's ~71M individual Python string objects alive at once before blocking even starts — this alone plausibly accounts for the bulk of the observed ~10 GB, not just the `.copy()`/dict issues fixed in round 1. `build_id_codec`'s `dict(zip(all_ids.values, codes))` (~12.4M-entry Python dict) added a further confirmed ~1.1 GB on its own.
- **Strategy shift (round 2, in progress)**: rather than continuing to chase individual copies, restructuring Sections 2-4 to reduce baseline footprint structurally: (a) load with `dtype="string[pyarrow]"` instead of plain `object` — Arrow-backed strings avoid per-object Python overhead, typically 2-4x smaller for large text columns; (b) convert `country` (only 3-4 unique values across 10M+ rows) to `category` immediately on load — near-total elimination of that column's cost; (c) convert the 3 derived key columns to `category` too, since blocking keys are exactly where massive value-repetition exists; (d) drop raw `business_name`/`business_address` from the main pool working frame entirely once keys + `id_code` are built, persisting them to a Parquet file on disk keyed by `entity_id` instead — Section 7 (`add_features`) then reads back only the rows for the (much smaller) candidate set, rather than keeping full raw text resident for all 10M+ pool rows for the whole pipeline; (e) `build_id_codec` rewritten to slice `pd.factorize`'s output array directly instead of building an intermediate Python dict + `.map()`.
